# Coin Analysis: Technical Debt

A standing reference to the project's outstanding technical debt. It records what is still open, weighs whether each item is worth doing and gives the rationale. Every item is a behaviour-preserving internal concern: nothing here proposes reverting a feature or changing any UI or UX behaviour. Scope is the whole repository: the `app` package, the training and packaging scripts at root, the bundled image data under `data/` and the GitHub Pages site under `docs/`.

Read the last section first. This project has a settled decision about its own future direction, and several items that would otherwise look like obvious next steps are ruled out by it.

The shipped capability, a hybrid of `pytesseract` OCR and a scikit-learn classifier with confidence scoring, works and is finished. This file is about the repository around it.

---

## 1. `data/raw_backup/` duplicates 1316 files that already exist in `data/raw/`

`data/raw/` holds 1896 tracked JPEGs. `data/raw_backup/` holds 1316, and every one of them has an identical relative path under `data/raw/`: same year-and-mint directory names, same filenames. It is a partial snapshot of the live dataset, taken before some processing step and then committed.

On disk that is 129 MB duplicating 129 MB of the 150 MB beside it. In git it is worse, because every one of those blobs is in history permanently.

Git already holds every prior state of `data/raw/`. A tracked backup directory adds nothing that `git checkout` cannot provide, and it costs every clone of this repository a second copy of the training set. It also creates a real ambiguity: anyone counting images, training a model or auditing the dataset has to know which of the two directories is authoritative, and nothing in the repository says.

Delete `data/raw_backup/` and add it to `.gitignore` so a future local backup cannot be committed. This is the single largest improvement available here and it removes no capability.

## 2. Trained model binaries are tracked

`data/models/coin_model_custom/` holds four pickled artefacts: `classifier.pkl`, `feature_extractor.pkl`, `label_encoder.pkl` and `confusion_pairs.pkl`.

Two problems, one practical and one about trust:

- They are build output. `train_custom_model.py` produces them from `data/raw/`, so they are derived data being versioned as source. Every retrain writes four new binary blobs into history.
- Pickle executes arbitrary code on load. A `.pkl` in a public repository is something a reader is invited to download and unpickle, and there is nothing in the repository telling them where it came from or that they should only load their own.

The application needs a model present to run, so simply deleting them breaks it. The proportionate answer is to publish them as a release asset and have the app fetch or expect a locally-trained model, with `train_custom_model.py` documented as the way to produce one. If they must stay tracked, they belong under Git LFS with a note in `README.md` saying they are generated by `train_custom_model.py` and should be regenerated rather than trusted.

## 3. `app/ui/main_window.py` is 1242 lines with twenty-eight broad exception handlers

The largest file in the repository by a factor of two, and it carries more `except Exception as e` blocks than the rest of the codebase combined. They are nested deeply: several sit at six to eight levels of indentation, inside loops inside conditionals inside other handlers.

Three of them print rather than log (`"Error in probability adjustment"`, `"OCR processing error"`), so the diagnostic goes to a console a windowed application does not have.

The shape tells the story: OCR and classification both fail in many ways on real photographs, and each failure was handled where it appeared. The result is a file where the control flow is mostly error handling, and where a genuine defect is indistinguishable from an expected degradation.

The valuable move is not to reduce the file to 400 lines for its own sake. It is to lift the analysis pipeline out of the window entirely: the sequence of preprocess, OCR, classify, score and reconcile is application logic that currently exists only inside Qt callbacks, which is why it cannot be tested and why every failure had to be handled inline. Moving that sequence into a plain module underneath the UI would let the handlers collapse into one place and would make item 4 achievable.

`batch_widget.py` (630), `results_widget.py` (591) and `image_widget.py` (575) sit behind it with the same character.

## 4. One test file, no coverage gate and no structural test

`tests/test_app.py` is the entire suite, against roughly 6,100 lines of Python. There is no coverage configuration, no `--cov-fail-under`, no `pyproject.toml` and no structural test.

This is the least-tested project in the portfolio by a wide margin, and it is the one doing the most probabilistic work: OCR confidence, classifier probability and the reconciliation between them are exactly the kind of logic where a defect produces a plausible wrong answer rather than a crash.

The realistic target is not 100% across the tree, because the Qt widgets and the OCR engine are not worth chasing. It is a gate over the parts that decide: `app/processing/preprocessor.py`, `app/models/classifier.py` and whatever comes out of item 3. Scope the gate to those, in the same way Trainer scopes to `src/core` and MMSP scopes to its validators.

## 5. No `ARCHITECTURE.md`, no `VERSION`, no packaging metadata

The repository has `README.md` and `LICENSE` and nothing else in the way of project documentation. There is no `pyproject.toml` (only `requirements.txt`), no `VERSION` file and no version string anywhere.

`package.py` at root suggests a packaging step exists, so something is being built and shipped without a version attached to it.

The `app` package does have a shape (`processing`, `models`, `utils`, `ui`) that is close to the portfolio's usual layering, and writing that down is cheap. A short `ARCHITECTURE.md` naming the four packages, the dependency direction and the analysis pipeline would also give item 3 a target to move code toward.

## 6. Root is a mix of application, training and utility scripts

`augment_data.py`, `count_images.py`, `train_custom_model.py`, `test_custom_model.py`, `package.py` and `run.py` all sit at root with no directory separating the launcher from the data-science tooling.

`test_custom_model.py` is the worst of it: the name looks like a pytest module and it is not one, so it will be collected or skipped depending on how the suite is invoked, and either outcome is confusing.

Move the training and data tooling into `tools/` (or `training/`), leave `run.py` at root as the launcher, and rename `test_custom_model.py` to something that does not collide with the test namespace (`evaluate_custom_model.py`).

---

## Looks like debt, not worth touching

- The 1896 JPEGs in `data/raw/`. That is the training set and it is the product's substance. Item 1 concerns only the duplicate copy beside it.
- `app/models/classifier.py` at 390 lines. Inside the danger band, so it wants taking to 350 when next touched, but nothing enforces the cap here so nothing will force it.
- The eleven `ocr_*.md` planning documents in the working tree (`ocr_enhancement_plan.md`, `ocr_next_steps.md`, `ocr_handoff_document.md` and the rest). They are correctly untracked. They are also the paper trail of the abandoned direction described below, so they should stay untracked and should not be revived as a work list.
- `requirements.txt` without a `pyproject.toml`. Covered by item 5; on its own it works.
- The `docs/` site being two hand-written pages. At that size a generator would cost more than it saves.

## Not debt (do not "fix" these)

These look like candidates but are correct as they stand; changing them would regress or add cost for nothing.

- **The deeper ML enhancement is abandoned, deliberately and permanently.** This is the most important entry in the file. The OCR-plus-classifier hybrid that ships is finished; the further machine-learning work explored in the untracked planning documents is not paused, it is closed. The reason is a property of the world rather than of the code: numismatic training data for the earlier decades is fundamentally incomplete, so no amount of model work recovers the accuracy those years would need. Nothing above should be read as an invitation to resume it. Item 4 asks for tests around what exists; item 3 asks for the existing pipeline to become testable. Neither means new modelling.
- **The hybrid confidence scoring itself.** Combining an OCR reading with a classifier probability, rather than trusting either alone, is the design decision that makes the tool work on real photographs. Do not simplify it to one signal.
- **`pytesseract` as an external process dependency.** Bundling an OCR engine would be a far larger cost than requiring one.
- **The scikit-learn feature choices (HOG and LBP) and the pickled `label_encoder`.** Settled, and part of the finished capability. Item 2 concerns where those files live, not what they contain.
- **GPL-3.0.** The portfolio default.
